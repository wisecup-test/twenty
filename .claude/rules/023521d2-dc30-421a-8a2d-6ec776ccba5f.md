These rules are ALWAYS ACTIVE for all files implementing custom visual effects hooks in the design system, particularly within website sections and feature cards.
</rule_activation>

### Rules

- **R-CANVAS-001** SHOULD: Complex visual effects (halftone processing, animated graphics) SHOULD use canvas APIs rather than CSS-only solutions for performance-critical rendering.

### Verify

```bash
# Count custom effect hooks following naming pattern
find . -path '*/hooks/use-*.ts' -type f | grep -E '(halftone|canvas|layout|effect)' | wc -l

# Verify canvas and animation frame usage in hooks
grep -r 'requestAnimationFrame\|canvas\.getContext' --include='use-*.ts' | wc -l

# Verify cleanup logic in effect hooks
grep -r 'useEffect.*return.*=>.*cancel' --include='use-*.ts' packages/twenty-website-new/src/sections/ | wc -l
```

**Accept when:**
- At least 3 custom effect hooks exist following the 'use-[effect-name]' naming pattern in the website sections
- All canvas-based effect hooks properly implement cleanup logic using useEffect return functions
- Effect hooks are colocated within 'hooks/' subdirectories of their consuming components or sections

### Implementation Guidance

- Create a shared utilities module for common canvas operations (context setup, animation frame management, cleanup patterns)
- Document the standard hook structure including useEffect for lifecycle, useRef for canvas elements, and cleanup patterns
- Establish naming conventions: 'use-[effect-name]' for hooks, colocate in 'hooks/' subdirectories within component folders
- Add TypeScript types for hook return values and configuration parameters
- Ensure all canvas effects are decorative only or provide equivalent ARIA labels and semantic HTML alternatives
- Implement performance monitoring and provide fallback options for low-end devices
