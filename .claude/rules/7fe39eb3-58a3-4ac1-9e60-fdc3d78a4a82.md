<rule_activation id="7fe39eb3-58a3-4ac1-9e60-fdc3d78a4a82" title="Adopt Zapier Integration Pattern for External API Exposure: External Endpoints Use" applies_to="**/*">
These rules are ALWAYS ACTIVE for all files matching external API endpoints, Zapier integration triggers and actions, external API packages, type definitions, and object metadata discovery endpoints.
</rule_activation>

### Rules

- **R-ZAPIER-001** MUST: All external API endpoints MUST use strongly-typed data structures defined in dedicated type definition files.
- **R-ZAPIER-002** MUST: All external data contracts MUST be defined in dedicated `.types.ts` files with comprehensive JSDoc documentation.
- **R-ZAPIER-003** MUST: Standard trigger patterns (list_record_ids for polling, trigger_record for webhooks, find_object_names for dynamic configuration) MUST be implemented in integration packages.
- **R-ZAPIER-004** MUST: Integration packages MUST follow the established `packages/twenty-{platform}` naming convention.
- **R-ZAPIER-005** MUST: Modern build tooling (Vite or equivalent) MUST be configured for integration packages.
- **R-ZAPIER-006** MUST: OAuth 2.0 authentication, rate limiting, audit logging, and scope-based permissions MUST be implemented for all external API endpoints.
- **R-ZAPIER-007** SHOULD: Integration documentation and visual components SHOULD be co-located in website sections for improved discoverability.
- **R-ZAPIER-008** SHOULD: Comprehensive error handling and logging SHOULD be implemented to aid debugging of integration issues.

### Scope

**In scope:**
- All Zapier integration triggers and actions
- External API packages (twenty-zapier, similar third-party integrations)
- Public API documentation and marketing materials
- Type definitions for external data contracts
- Object metadata and discovery endpoints

**Out of scope:**
- Internal GraphQL APIs used by first-party clients
- Direct database access patterns
- Internal service-to-service communication
- Admin-only APIs and tooling
- Development and testing utilities

**Exceptions:**
- EXC-001: Legacy integrations built before this pattern was established may use alternative structures

### Verify

```bash
# Verify integration packages exist with platform-specific naming
find packages -type d -name 'twenty-*' | grep -E '(zapier|integration)' | wc -l

# Verify standard trigger patterns are implemented
grep -r 'list_record_ids\|find_object_names\|trigger_record' packages/twenty-zapier/src/triggers/ | wc -l

# Verify type definition files exist for external data contracts
find packages/twenty-zapier -name '*.types.ts' -o -name 'data.types.ts' | wc -l

# Verify modern build tooling is configured
grep -r 'vite.config' packages/twenty-zapier/ | wc -l
```

**Accept when:**
- At least one integration package exists under `packages/` with platform-specific naming (e.g., `twenty-zapier`)
- Standard trigger patterns (`list_record_ids`, `find_object_names`, `trigger_record`) are implemented in the integration package
- Type definition files exist for external data contracts
- Modern build tooling (Vite or equivalent) is configured for integration packages
- OAuth 2.0 authentication is implemented for external API endpoints
- Rate limiting and audit logging are configured
- Comprehensive JSDoc documentation exists in `.types.ts` files

<enforcement>
Claude Code MUST NOT skip or defer verification. All external API endpoints MUST comply with R-ZAPIER-001 through R-ZAPIER-006. CI pipeline MUST fail if integration packages are missing required trigger patterns or type definitions. Pull requests MUST be blocked if external API changes are not reflected in integration package types. Security scanning MUST flag any direct database access or internal schema exposure in integration code.
</enforcement>
